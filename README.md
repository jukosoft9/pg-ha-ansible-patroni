# PostgreSQL 17 HA with Patroni, etcd & PgBouncer - and an Online Partitioning Migration

Everything is Infrastructure as Code (Vagrant + Ansible) and
reproducible from a clean environment in one command; Phase 2 is a live, throttled, crash-safe
migration from an unpartitioned table to monthly partitions.

| Brief requirement | Where / how |
|---|---|
| 3 PostgreSQL 17 nodes + Patroni | `ansible/roles/postgresql`, `ansible/roles/patroni` |
| DCS across the 3 nodes | 3-member **etcd** cluster (`ansible/roles/etcd`), mutual TLS |
| Connection pooler | **PgBouncer on every node** (`ansible/roles/pgbouncer`), TLS both sides |
| Reusable roles, idempotent, no hard-coded secrets | 6 roles; 2nd run = `changed=0`; secrets in **Ansible Vault** |
| Automatic bootstrap, leader election, failover | Patroni + etcd; measured below |
| 2M-row legacy table, partitioned target | `migration/sql/legacy_table.sql`, `seed_legacy.sql`, `modern_table.sql` |
| Throttled, checkpointed migration (25k batches, sleep, resume) | `migration/migrate.py` |
| Drop the flat table after migrating the window | `migrate.py cutover` + `migrate.py purge` |

## Architecture

```
                         Clients / application  (psycopg, psql)
          libpq multi-host: host=pg1,pg2,pg3 port=6432 target_session_attrs=read-write
                                    | TLS (verify-full)
       +----------------------------+----------------------------+
       |                            |                            |
+------v--------+            +------v--------+            +------v--------+
| pg1 .56.11    |            | pg2 .56.12    |            | pg3 .56.13    |
| PgBouncer:6432|            | PgBouncer:6432|            | PgBouncer:6432|
|   | TLS       |            |   | TLS       |            |   | TLS       |
| PostgreSQL 17 |<--stream---| PostgreSQL 17 |---stream-->| PostgreSQL 17 |
|  (replica)    |  TLS repl  |  (leader)     |  TLS repl  |  (replica)    |
| Patroni :8008 |            | Patroni :8008 |            | Patroni :8008 |
|  (HTTPS API)  |            |  (HTTPS API)  |            |  (HTTPS API)  |
| etcd 2379/2380|<==========>| etcd 2379/2380|<==========>| etcd 2379/2380|
+---------------+   mTLS     +---------------+    mTLS    +---------------+
         \______________ 3-member etcd cluster = Patroni DCS ______________/
```

* **Leader election:** Patroni keeps a leader key in etcd with a TTL (30 s). If the primary stops or
  loses etcd, the key is released/expires and the most up-to-date replica (within
  `maximum_lag_on_failover` = 1 MB) is promoted. `use_pg_rewind` + data checksums let a failed
  primary rejoin as a replica without a full re-clone.
* **Pooling / leader discovery:** each PgBouncer pools only for its **local** PostgreSQL. Clients
  list all three PgBouncers and libpq picks the read-write one (`target_session_attrs=read-write`).
  Production alternative: HAProxy / VIP health-checking Patroni's `/primary` endpoint.

### Encryption on every hop (private CA generated by Ansible)

| Path | Protection |
|---|---|
| etcd peer (2380) and client (2379) | mutual TLS - only certs signed by the cluster CA |
| Patroni REST API (8008) | HTTPS; health endpoints readable, state changes need basic auth |
| Replication / pg_rewind | `hostssl` + SCRAM, `sslmode=verify-full` |
| Client -> PgBouncer (6432) | TLS required (`client_tls_sslmode=require`), plain text refused |
| PgBouncer -> PostgreSQL | TLS, `server_tls_sslmode=verify-full` |

PgBouncer terminates TLS (decrypt -> pool -> re-encrypt), so it is "encrypted on every hop" rather
than strictly end-to-end - normal for any pooler; the pooler host is inside the trust boundary.

## Phase 1 - deploy the HA cluster from scratch

### Prerequisites

* Hypervisor: **VMware Workstation/Fusion + `vagrant-vmware-desktop`** (tested) or **VirtualBox**.
* Vagrant 2.4+, ~8 GB free RAM (VMs default to 2 vCPU / 2.5 GB; override with `PG_VM_CPUS`, `PG_VM_MEMORY`).
* A Linux/macOS/WSL2 control node with **Ansible core 2.15+**, `python3-cryptography`, `git`, `psql`.

### Steps

```bash
# 1. Control-node SSH key, authorised on the VMs by Vagrant
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519 -N ""          # if you don't have one
mkdir -p keys && cp ~/.ssh/id_ed25519.pub keys/ansible.pub

# 2. VMs (from the repo root; on VMware add --provider=vmware_desktop)
vagrant up

# 3. Secrets: create your own vault (the committed vault.yml is encrypted with the author's key)
openssl rand -base64 32 > ~/.vault_pass_pg-ha && chmod 600 ~/.vault_pass_pg-ha
cd ansible
cp group_vars/all/vault.yml.example group_vars/all/vault.yml   # edit the values
ansible-vault encrypt group_vars/all/vault.yml

# 4. Deploy (about 4 minutes) - then run again to prove idempotency (changed=0)
ansible-galaxy collection install -r requirements.yml
ansible-playbook site.yml
ansible-playbook site.yml
```

**Windows 10 + WSL2 control node only:** WSL2 sits behind its own NAT, so after each Windows
reboot run `scripts/windows/enable-wsl-routing.ps1` in an **admin** PowerShell. The Vagrantfile adds
the matching return route on each VM (`PG_CONTROL_SUBNET=""` disables it on Linux/macOS hosts).

### Verify

```bash
ssh vagrant@192.168.56.11 'sudo -i patronictl list'          # 1 Leader + 2 streaming Replicas
ssh vagrant@192.168.56.11 'sudo -i etcdctl endpoint status -w table'
for ip in 192.168.56.11 192.168.56.12 192.168.56.13; do      # only the leader returns 200
  echo "$ip $(curl -s -o /dev/null -w '%{http_code}' --cacert ansible/pki/ca.crt https://$ip:8008/primary)"
done
```

### Failover demonstration

```bash
. migration/env.sh && scripts/failover-probe.sh               # terminal 1: 1 write/s, prints the leader
ssh vagrant@<leader-ip> 'sudo systemctl stop patroni'         # terminal 2: stop the primary's service
ssh vagrant@192.168.56.11 'sudo -i patronictl list'           # new leader, timeline +1
ssh vagrant@<old-leader-ip> 'sudo systemctl start patroni'    # old primary rejoins as a replica
ssh vagrant@192.168.56.11 'sudo -i patronictl switchover --candidate pg2 --force'   # planned move
ssh vagrant@192.168.56.11 'sudo -i patronictl history'
```

| Scenario (measured with the probe) | Write outage |
|---|---|
| Planned switchover | ~3 s |
| Primary's Patroni service stopped | ~4 s (leader key released immediately) |
| Primary host hard crash | bounded by the 30 s leader TTL + one HA loop |

## Phase 2 - online partitioning & throttled migration

### Design

| Stage | Mechanism | Why it is safe on a live system |
|---|---|---|
| Target schema | `transaction_logs_modern` + monthly partitions (window + 3 future months) + DEFAULT | DEFAULT means an unexpected date never fails an insert |
| Live changes | `AFTER INSERT/UPDATE/DELETE` trigger mirrors in-window changes with **upserts** | runs in the application's transaction - never blocks it, never misses a write |
| Backfill | keyset batches of **25,000** by `id`, up to a high-water mark captured **after** the trigger exists | rows below the mark are copied, rows above are mirrored: complete coverage |
| Idempotency | batch `INSERT ... ON CONFLICT DO NOTHING` **and** checkpoint `UPDATE` in **one transaction** | a crash loses only the uncommitted batch, redone on restart - no duplicates or PK conflicts |
| I/O safety | `--sleep` between batches (default 1 s) + back-off while replica replay lag > `--max-lag-mb` | protects disk I/O on the primary and the replicas |
| Failover | libpq multi-host reconnect + retry | migration resumes on the new leader from the checkpoint |
| Verification | full-row `EXCEPT ALL` both ways at one `REPEATABLE READ` snapshot (`--fix` reconciles) | proves the target equals the source window |
| Cutover | one transaction, `lock_timeout` 1 s, retried: drop trigger, rename flat -> `_retired`, create compatibility **view** `transaction_logs_flat` | application keeps writing unchanged; lock held for milliseconds |
| Purge | `DROP TABLE transaction_logs_flat_retired` | removes rows older than the window; a drop only unlinks files |

"Last 3 months" = from the 1st of the month three months back (UTC), aligned to partition boundaries,
computed once and stored in `migration_config`.

### Run it

```bash
python3 -m venv ~/.venvs/pg-ha && ~/.venvs/pg-ha/bin/pip install -r migration/requirements.txt
source ~/.venvs/pg-ha/bin/activate
. migration/env.sh                                   # TLS verify-full, leader discovery, vault password

psql -v ON_ERROR_STOP=1 -f migration/sql/legacy_table.sql
psql -v ON_ERROR_STOP=1 -f migration/sql/seed_legacy.sql     # 2M rows, ~45 s
psql -v ON_ERROR_STOP=1 -f migration/sql/modern_table.sql
psql -v ON_ERROR_STOP=1 -f migration/sql/sync_trigger.sql
psql -f migration/sql/test_sync_trigger.sql

python migration/load_generator.py --rate 50          # separate terminal: live application writes
python migration/migrate.py run --sleep 1.0           # Ctrl+C or kill -9 at any time, then re-run
python migration/migrate.py status
python migration/migrate.py verify
python migration/migrate.py cutover
python migration/migrate.py purge

psql -f migration/sql/reset_phase2.sql                # start the demo again from scratch
```

### Measured results (50 ops/s live write load)

| Metric | Result |
|---|---|
| Rows migrated | 593,822 copied in 24 batches (+ live rows mirrored by the trigger) |
| Batch time | ~270-960 ms per 25k rows, 1 s sleep between batches |
| Application latency during backfill | p50 ~3 ms, max < 50 ms, **0 errors** |
| `kill -9` mid-batch | in-flight batch rolled back; resume continued at `last_id + 1`, no duplicates |
| Backfill / trigger overlap | last batch skipped 245 rows already updated by the app (newer version kept) |
| Leader disk | 3-7 % utilisation, ~1 ms write latency |
| Verification | source window = target, 0 missing / 0 extra |
| Cutover | lock waited 2 ms, **held 46 ms**, application unaffected |
| Purge | legacy table (218 MB) dropped; queries now prune to a single partition |

## Key design decisions

* **Patroni owns PostgreSQL:** `create_main_cluster = false` before package install, distro service
  disabled, Patroni's unit uses `KillMode=process` so stopping it releases the leader key cleanly.
* **etcd pinned and checksum-verified** (official release + `SHA256SUMS`), all members started in
  parallel (bootstrap needs quorum), config changes roll one member at a time (`throttle: 1`).
* **Config changes reload, never restart** Patroni (a restart on the leader would fail over).
* **PgBouncer `auth_query`** through a `SECURITY DEFINER` function; superusers are excluded from the
  lookup *and* rejected in PgBouncer's hba; the admin console is reachable only via local peer auth.
* **Failover testing:** PgBouncer caches server-reported parameters (`in_hot_standby`), so
  after a role change libpq's `target_session_attrs` picks the wrong node and writes failed for
  minutes. Fixed with a Patroni `on_start`/`on_role_change` callback that restarts the local
  PgBouncer (least-privilege sudo rule for that one command). Write outage dropped to ~3 s.
* **Idempotency everywhere:** `blockinfile`, `creates:`, check-then-create SQL, `no_password_changes`.

## Limitations and Next steps

* Certificate rotation (Vault PKI / cert-manager); certs are valid for 2 years.
* `watchdog: required` (softdog) to fence a hung primary; Patroni `synchronous_mode` for RPO = 0.
* HAProxy or a VIP in front of the poolers instead of client-side multi-host.
* Backups and PITR (pgBackRest), monitoring (postgres_exporter, Prometheus, Grafana).
* Schedule `create_logs_partitions()` monthly (pg_cron) and alert if the DEFAULT partition grows.
* After cutover, point the application at `transaction_logs_modern` and drop the compatibility view.
* Use a dedicated migration role rather than the application user; archive rows to object storage
  before the purge if retention requires it.
